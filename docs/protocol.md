# UDP 线协议

> 一句话：**一个端口，四种东西**——`PING`、`HELLO`、`STOP`、裸 PCM。

板子是 UDP 服务端，固定监听 **5005**。电脑是客户端，主动发第一个包。

```
                 ┌─────────┐                        ┌─────────┐
   PING ────────►│         │────────► PONG          │         │
   HELLO ───────►│         │────────► READY         │         │
                 │  board  │                        │  board  │
   STOP ────────►│  :5005  │◄──────── PCM 1280 B    │  :5005  │
                 │         │          (20 ms)       │         │
   0xAA+PCM ────►│         │                        │         │
                 └─────────┘                        └─────────┘
                    上行（麦克风）                 下行（喇叭）
```

---

## 1. 音频格式（两个方向都一样）

| 项 | 值 |
|---|---|
| 采样率 | 16000 Hz |
| 位深 | 16 bit，小端（s16le） |
| 声道 | **2（立体声）** |
| 一帧 | 4 字节 |
| 码率 | 512 kbit/s |
| 上行包长 | **1280 字节 = 320 帧 = 20 ms** |
| 下行包长 | 任意 4 的倍数，建议 **640 字节 = 10 ms** |

麦克风是单声道的，数据在**左声道**，右声道是静音（INMP441 的 L/R 接地时就是这个行为）。
板子仍然按立体声发，是为了让每包帧对齐、两端代码都不用处理奇数字节。

> 想省带宽？改成 8 kHz 单声道能降到 128 kbit/s，但你得同时改固件（`config.h` 的
> `SAMPLE_RATE` / `SAMPLE_CHANNELS`）、客户端和协议文档。不值得，除非你真的在窄带宽链路上。

---

## 2. 命令

命令是 **ASCII 文本**，不带任何包头，不带长度字段。板子会把收到的前 31 个字节当字符串，
去掉结尾的 `\r`/`\n`，然后**整串精确比较**。所以 `HELLO`、`HELLO\n` 都可以，`hello` 不行。

| 命令 | 方向 | 板子回复 | 作用 |
|---|---|---|---|
| `PING` | 电脑 → 板子 | `PONG` | 探活。**不改变推流状态** |
| `HELLO` | 电脑 → 板子 | `READY` | 开始把麦克风推给**这个源地址**，并清零统计 |
| `STOP` | 电脑 → 板子 | 无 | 停止推流 |
| 其他 | 电脑 → 板子 | 无 | 记一条日志，忽略 |

回复也是纯 ASCII，不带换行、不带长度字段，用 `startswith` 判断即可。

### 谁是我该推给谁

板子**不配置对方 IP**，而是记住 `HELLO` 的来源地址 `(ip, port)`，之后所有上行音频都发给它。

- 电脑换个 IP、换个端口，只要重新发一次 `HELLO` 就行，不用重新烧固件。
- **只记一个 peer**：后发的 `HELLO` 覆盖前面的。多台电脑想同时听，得改固件（见 §7）。
- 所以：**接收和发送请用同一个 socket**，否则 `HELLO` 的源端口和你监听的端口对不上，
  包会发到一个没人听的端口上（这是最常见的「PING 通但没有声音」）。

## 3. 两种包怎么区分

- **上行（板子 → 电脑）**：没有包头。任何收到的包都是裸 PCM。
  > 不对称是故意的：上行每秒 50 个包，多一个字节就是多 512 kbit/s 里的一部分，
  > 而且板上没有任何别的数据要发上来，加头没意义。
- **下行（电脑 → 板子）**：**第一个字节必须是 `0xAA`**，后面才是 PCM。否则板子会把它当文本命令。

下行发音频时，长度会按 4 字节向下取整（不是整帧的尾巴会被丢掉，不会让后面的帧错位）。

## 4. 状态机

```
        ┌────────┐  HELLO   ┌───────────┐
        │  idle  │─────────►│ streaming │
        │        │◄─────────│           │
        └────────┘   STOP   └───────────┘
             ▲                     │
             └─────────────────────┘
                  上电 / 重启
```

- `idle`：只响应 `PING` / `HELLO`，不收麦克风、不推流。下行音频**照常播放**（板子不知道你在不在说话）。
- `streaming`：每 20 ms 从 I2S 读一块，发出去。状态在串口里每 3 秒打印一次统计。

**没有自动超时**（`config.h` 里 `STREAM_IDLE_TIMEOUT_MS = 0`）。
这意味着如果电脑崩了、没来得及发 `STOP`，板子会一直推流到重启为止。
对「电脑上跑的程序」来说这通常没问题；如果你要做长期无人值守的设备，
把它设成 30000（30 秒），并且让客户端在录音/听写期间定期发 `PING` 当心跳。

## 5. 可靠性与丢包

这套协议**没有**序号、没有重传、没有校验、没有时间戳。这是权衡后的选择：

- 局域网 UDP 丢包率实测接近 0（45 秒 / 2254 包连续推流，零丢包）。
- 语音流重传没有意义——迟到的包不如不要。
- 加了序号就得处理乱序、就得做抖动缓冲，而这两件事**在客户端做更合适**：
  你知道自己有多少缓冲、能忍多少延迟。

客户端该做的：

1. **丢弃开头的 ~300 ms**。刚 `HELLO` 之后 I2S DMA 里是启动毛刺，能量很大会误触发任何能量门限。
2. **用字节数估时长**：`时长 = 收到的字节数 / 64000`（16 kHz × 4 B）。丢包会直接体现为时长偏短。
3. **要判断卡顿**：记录「距离上一个包多久」，超过 1.5 秒就认为链路断了（板子掉线 / Wi-Fi 切换）。
4. **不要假设包长固定**：板子一般发 1280 字节，但 I2S 读到的可能略少，按实际长度拼接即可。

## 6. 带宽、MTU、防火墙

- 单向 512 kbit/s，双向同时跑约 1 Mbit/s。2.4 GHz Wi-Fi 完全够。
- 下行最大包 = 1 + 1280 = 1281 字节，不会超过 1500 MTU，不需要分片。
- **Windows 防火墙默认会拦「入站 UDP」**。现象很典型：`PING` 有回音（出站放行），
  但 `HELLO` 之后一个音频包都收不到（入站被拦）。第一次运行客户端时放行 `python.exe` 即可。
- 板子只支持 **2.4 GHz**（ESP32-S3 没有 5 GHz 射频）。SSID 填 5 GHz 的会连不上，
  串口里表现为「连了 10 次都失败，放弃」。
- 如果电脑上开着 VPN / 代理软件（Clash、FlClash 的 TUN 模式等），
  它可能抢走 `192.168.x.x` 的路由，导致「板子在、电脑也在，就是不通」。
  排查：`Find-NetRoute -RemoteIPAddress <板子IP>`，看走的是不是本地网卡；
  规则里加 `IP-CIDR,192.168.0.0/16,DIRECT` 即可。

## 7. 想扩展的话

协议是刻意留了余地的，下面这些都不需要改包格式：

| 想加的东西 | 怎么加 |
|---|---|
| 多客户端同时听 | 把 `peer` 改成数组（最多 N 个），`HELLO` 时追加，`STOP` 时移除 |
| 板子主动上报状态（音量、温度） | 新命令 `STAT`，回复一行 JSON；注意别和音频包混在一起 |
| 加密 | 在 UDP 上套 DTLS，或者整条链路走 WireGuard/Tailscale |
| 压缩 | Opus 每 20 ms 一帧，正好替换现在的 1280 字节包；板子端用 `esp-opus` |
| 时钟同步 | 加时间戳字段，客户端做自适应抖动缓冲 |

改之前先读 [architecture.md](architecture.md)：里面有几条「看起来能简化、实际会炸」的记录。
