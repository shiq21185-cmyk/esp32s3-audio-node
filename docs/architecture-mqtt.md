# MQTT 版的架构与设计取舍

> UDP 版的取舍见 [architecture.md](architecture.md)，那套只在本项目 `firmware/audio-node` 里有效。
> 这一页只讲 MQTT 版多出来的东西：**为什么加、加了什么、哪些地方和 UDP 版不一样**。

---

## 1. 一句话区别

UDP 版：**电脑主动连板子**。板子的 IP 必须可路由，两端必须同一张网。
MQTT 版：**两端都主动连 broker**。谁在 NAT 后面、IP 变成多少都不重要。

为了让这句话成立，多付出的代价：

| 代价 | 具体 |
|---|---|
| 一个中转 | 要有一台公网可达的 broker（自建 5 分钟，见 [protocol-mqtt.md](protocol-mqtt.md) §11） |
| 延迟 | 多一跳。实测同城 broker 单向多 10~30 ms |
| 包率限制 | 托管 broker 常按「每秒消息条数」限流 ⇒ 包长从 60 ms 改成 120 ms |
| 隐私 | 音频经过第三方（除非自己架 broker）。这也是为什么要随机 base + 账号密码 |

## 2. 固件里的五个任务

| 任务 | 优先级 | 栈 | 干什么 |
|---|---|---|---|
| `spk_task` | 6 | 4 KB | 从 StreamBuffer 取音频，**永远**写 I2S1（喇叭） |
| `mic_task` | 5 | 8 KB（不够就 64 KB） | 读 I2S0（麦克风），算 RMS、过门限、塞进上行缓冲 |
| `enc_task` | 4 | 40 KB（PSRAM） | 从上行缓冲取整帧 → Opus 编码 → 攒 3 帧打包 publish |
| `dec_task` | 4 | 40 KB（PSRAM） | 下行包 → 拆包/解码 → 写进喇叭 StreamBuffer |
| `btn_task` | 3 | 3 KB | 板载按键：强制开麦 / 随身模式送话窗口 |
| `rep_task` | 2 | 4 KB | 定时 publish state |

**为什么编码单独一个任务**：一次 Opus 编码实测 200 µs ~ 24 ms。放在 `mic_task` 里
会拖慢 I2S 读取，读慢了就丢音频（I2S DMA 环形缓冲只有几十毫秒）。
`mic_task` 只做「读 + 算 RMS + 塞缓冲」，绝不做编码。

**为什么 enc/dec 的栈要放 PSRAM**：乐鑫那个预编译 Opus 库的栈开销很大。
  8 KB —— 编第一帧就 `A stack overflow in task mic`，板子 panic 重启，
           表现是「一开麦就断线、上行永远是 0 包」。
  32 KB —— 建任务时内部 RAM 直接不够（内部只剩约 300 KB），任务根本没起来，
           表现是「计数器全是 0，连循环都没跑」。
所以走 `xTaskCreateWithCaps(..., MALLOC_CAP_SPIRAM)`，索性给 40 KB。

**优先级反直觉但重要**：喇叭（6）> 麦克风（5）。
麦克风慢 60 ms 没人听得出来（客户端会做缓冲）；喇叭慢 60 ms 就是**可听见的卡顿**。

## 3. 上行：为什么是 Opus 打包（0xAC）

裸 PCM 16k/16bit/单声道 = 32 KB/s = 115 MB/小时。走公网、用别人的 broker 或 4G 流量，
这个量级不可接受。Opus 16 kbit/s = 2 KB/s，**省 16 倍**。

但 Opus 一帧只有 60 ms，串行发出去就是 16.7 包/秒。实测这条链路（EMQX Serverless）
按**每秒消息条数**限流：

| 每包帧数 | 包率 | 投递率 |
|---|---|---|
| 1 帧 | 16.7 包/秒 | 55~60% |
| 2 帧 | 8.3 包/秒 | 94% |
| 3 帧 | 5.6 包/秒 | 100% |

包大小（20 / 40 / 60 / 121 / 200 字节）对丢包率**没有任何影响** —— 这条结论是把
包长和包率分别扫过一遍才敢下的。所以只能加大包、不能减小包。

代价：单向多 180 ms（3 帧 = 180 ms 的数据攒在一起才发）。

---

## 4. 下行：为什么回退成裸 PCM（0xAA）

Opus 下行的听感问题是「**前面正常，后面一卡一卡**」，而且断得很有规律。

当时查了很久，两个诱因叠加：

1. **每秒消息条数**限流把后段挤在路上（同上）。60 ms 一包时最严重。
2. **板子解码跟不上**。PC 边合成 TTS 边送料，送料率约 93% 实时（每个 60 ms 块自己要
   花几毫秒编码 + 加锁 + TLS 发布），板子的解码又占一份 CPU。两边的欠账累积在
   「从开口那一刻就在倒计时」的缓冲里，长句必卡在句尾。

最后的取舍：下行改裸 PCM，**播放路径上零计算**。多花 16 倍带宽（单向 256 kbit/s），
换「永远不会有解码欠账」。这个交换在本项目里值得 —— 下行总量受 TTS 时长限制，
不像上行那样「常开麦」。

留了兼容：板子仍然认 `0xAB`（单帧 Opus）和 `0xAC`（打包）。想省流量可以改回去。

## 5. 缓冲：从 64 KB 到 256 KB（8 秒）

`s_spk` 是喇叭 StreamBuffer，放 PSRAM，默认 256 KB ≈ 8 秒单声道。

演变过程（每次都是被同一个症状推着走的）：

- 24 KB（750 ms）：电脑稍微慢半拍就被抽干 → 补零 → 听感一顿一顿。
- 64 KB（2 秒）：症状变成「前面 10 个字左右流畅，后面卡」。10 个字 ≈ 2 秒，
  恰好等于缓冲被吃空的时间。
- 256 KB（8 秒）：欠账被吸收掉，用户听不出速度差。

**8 秒不嫌大**，因为缓冲只在「电脑送得比板子播得慢」时才积起来，正常使用时水位很低。
但它确实带来一个风险：如果电脑暂停送料，板子会**继续念完缓冲里的 8 秒**才静下来。
断电/急停时这是 8 秒的滞后 —— 本项目接受，因为优雅停止本来就要靠硬件。

## 6. 回声保护（echo guard）

麦克风和喇叭在一个壳子里 ⇒ 板子放出来的声音必被自己的麦克风收进去。

判据在板子上，不在电脑：**喇叭缓冲非空，或者刚写完不到 `SPK_TAIL_US`（120 ms）**，
这段时间不把麦克风的块送出去。

为什么不用「电脑发 `MIC 0`」来挡：

1. 电脑一时卡住（TTS 慢、GC、网络抖动）时来不及发 —— 这段声音就漏进公网了。
2. 将来做「边说边听」的打断，这一层必须兜住「听见自己 → 又接一句」的自激。

调试打断时用 `ECHO 0` 关掉。

## 7. 本地人声门限

麦克风开着 ≠ 一直上传。板子对每包 PCM 算 RMS：

- 只在**没人说话时**学房间底噪 `floor`（用「最近一批静音块的 20 百分位」，
  不是平均值 —— 平均值会被偶发的大噪声拉偏）。
- 门槛 = `floor × 3`，夹在 `[50, 250]`。
- 开口前带 5 包（300 ms）预录，防止吞第一个字；说完再传 1.2 秒，防止吞尾音。

屋内实测：安静房间底噪 rms 4~26，说话 160~300。

**为什么还要有按键模式**：街上/地铁里底噪比人声大，「比底噪高 3 倍」直接失效。
`MODE 1` 改成按键开一个 20 秒送话窗口，窗口内所有声音都传，不判门限。

## 8. state JSON 的那个坑（必读）

`publish_state()` 用一个定长 `char payload[N]` 拼 JSON。随着调试字段越加越多，
长度悄悄越过了缓冲区 —— `snprintf` **静默截断**，发出去的 JSON 不完整。

然后：

```
JSON 不完整 → 电脑侧 json.loads 抛异常 → 被 except 吞掉 → 状态永远是空的
           → 上层判断「板子没开机」→ 整段跳过音频
```

**收发全正常，只有「判断」那条链断了。** 这种 bug 最难查，因为所有音频指标都是绿的。

修法两条，都得留着：

1. `payload[768]`（原来 512）。加字段的同时就要想长度。
2. `snprintf` 的返回值要检查 —— 它返回「原本想写多少字节」，`>= sizeof(buf)` 就是截断了：
   ```c
   int n = snprintf(payload, sizeof(payload), ...);
   if (n < 0 || (size_t)n >= sizeof(payload)) {
       ESP_LOGE(TAG, "STATE JSON TRUNCATED: need %d bytes ...", n);
   }
   ```
3. 电脑侧解析失败**必须计数并打日志**，不能裸 `except: pass`。

## 9. 五个「看起来能简化、实际会炸」

1. **I2S 断流会无限重放最后那一小段**。所以播放任务永远在写，没声音就写零。
   不能「没数据就 return」—— 听着就像「喇叭一直卡着叫同一句」。
2. **`spkb` 不能当「收到的音频量」用**。它统计写进 I2S 的字节**含静音**，
   队列空时每 30 ms 也写一整块静音，所以一直线性涨。要看收到多少，用 `dpkts` / `dbytes`。
3. **`sbuf` 单位是字节，÷32 才是毫秒**。除以 1000 会得出「0 毫秒」和「64 毫秒」这种假结论。
4. **PC 侧不能一次性把音频灌进 broker**。会瞬间撑满板子缓冲（`ddrop` 涨）然后整段丢。
   必须按实时速度送。
5. **client_id 两端必须不同**。MQTT 同 id 是「后到者踢前者」。板子用 `board-<base>`，
   电脑用别的；否则两边会互相把对方顶下线，表现是「一会儿能通一会儿断」。

## 10. 和 UDP 版的分工

| | UDP 版 `firmware/audio-node` | MQTT 版 `firmware/audio-node-mqtt` |
|---|---|---|
| 适用 | 同一局域网、追求最低延迟 | 跨网、要带出门 |
| 需要公网 IP / 端口映射 | 不需要（局域网内） | 不需要（两边都出站） |
| 音频 | 立体声裸 PCM，512 kbit/s | 上行 Opus 16 kbit/s，下行单声道 PCM 256 kbit/s |
| 依赖 | 无（标准库） | 电脑侧要 paho-mqtt（+ 解码可选 PyAV） |
| 缓冲 | 48 KB（1.5 s） | 256 KB（8 s，PSRAM） |
| 代码 | 约 300 行 C | 约 1000 行 C |

两套互不影响，按场景挑一个烧。
