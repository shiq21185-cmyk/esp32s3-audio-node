# 架构与设计取舍

> 这一页记录的是「为什么这样写」，以及「哪几种看起来更聪明的写法试过、炸了」。
> 想改固件之前建议先扫一遍 §4。

---

## 1. 一句话架构

**板子只做 I/O，所有判断都在电脑上。**

```
┌──────────────────────── 板子（ESP32-S3）────────────────────────┐
│                                                                 │
│  INMP441 ──I2S1 RX──► udp_task ──► UDP:5005 ──► 电脑            │
│  MAX98357 ◄─I2S0 TX── spk_task ◄── UDP:5005 ◄── 电脑            │
│                          ▲                                      │
│                          └── StreamBuffer（48 KB，≈1.5 s）       │
└─────────────────────────────────────────────────────────────────┘

┌──────────────────────── 电脑 ───────────────────────────────────┐
│  录音 / 播放 / 语音识别 / 对话 / 合成 / 混音 / 打断 / 记忆 …      │
└─────────────────────────────────────────────────────────────────┘
```

为什么这么分：

- **理由一（能力）**：16 kHz 语音识别、大模型对话，在 S3 上跑不动；就算能跑，也只是把成本从电脑搬到板子上，没有任何收益。
- **理由二（迭代速度）**：改一行 Python 就能调参，改固件要编译 + 烧录 + 重新连 Wi-Fi。**音频调试 90% 的时间花在调参上**。
- **理由三（失败模式）**：板子跑飞了要人去按复位；电脑上的程序崩了，重启一个进程就行。

反过来说，如果你的场景是「必须离线、必须独立工作」，那这个架构就不合适——
你需要板子本地跑唤醒词 + 识别，那是另一个项目。

## 2. 固件里的两个任务

| 任务 | 优先级 | 栈 | 干什么 |
|---|---|---|---|
| `spk_task` | 6 | 4 KB | 从 StreamBuffer 取音频，**永远**写 I2S0 |
| `udp_task` | 5 | 8 KB | 收 UDP（5 ms 超时），分发命令 / 入缓冲；`streaming` 时读 I2S1 并发出去 |

优先级反直觉但重要：**喇叭比麦克风优先**。

- 麦克风慢 20 ms 没人听得出来（反正客户端要做抖动缓冲）；
- 喇叭慢 20 ms 就是**可听见的卡顿**，而且 I2S TX 一旦供不上就是爆音。

两个任务之间只有一个 `StreamBuffer`（单生产者单消费者，免锁），容量 48 KB ≈ 1.5 秒。
这个数字是权衡：

- 太小（比如 8 KB = 250 ms）：电脑稍微卡一下就断音；
- 太大（比如 256 KB = 8 秒）：你说完话到听见回复中间有 8 秒的「水库」要放空，交互感全毁。

1.5 秒是「容忍电脑抖动」和「不让延迟失控」之间的拐点。

## 3. 延迟预算

单向的固定成本：

| 环节 | 时间 |
|---|---|
| 麦克风 I2S 攒一个 20 ms 块 | 20 ms |
| UDP 局域网传输 | < 5 ms（Wi-Fi 省电关掉后是个位数） |
| 电脑侧抖动缓冲（你自己定） | 0 ~ 100 ms |
| 喇叭缓冲（建议维持 ≤ 100 ms） | 0 ~ 100 ms |
| **合计（不含你的处理）** | **约 25 ~ 230 ms** |

实际体感主要被电脑侧的处理吃掉：语音识别几百毫秒、大模型思考几秒、TTS 几秒。
**这套硬件不是瓶颈**，所以不要在固件上抠那 20 ms，去优化你的处理链。

## 4. 失败记录：这些写法试过，炸了

### 4.1 「没声音就停掉 I2S 写入」→ 喇叭无限重放最后一小段

症状：喇叭**一直在叫同一句**，停不下来，像卡带。

原因：ESP32 的 I2S TX 是 DMA 描述符环。你把最后一个缓冲区写完就撒手不干，
硬件会**循环重放**这个环，永远不停。这不是 bug，是设计——DMA 不知道你「说完了」。

第一反应是「那我少写点」或者「加个 vTaskDelay 让它播完」——都不行，
因为播完的那一刻环里还是那段数据，还是会重放。

正确做法（现在代码里的）：**播放任务永远在写**。没数据就写零，写零也是写。
配合 `tx_cfg.auto_clear = true`，双保险。

推论：任何「流式」音频源（TTS 边生成边播）也必须遵守这条——
**音频源断供的时候，要主动灌静音，不能什么都不做。**

### 4.2 尾音被吃掉

症状：最后半秒的话听不清，像被掐断。

原因：同上，最后 20 ms 还没被 DMA 播完，环就回到开头了。
现在客户端 `play_pcm` 会在结尾补 400 ms 静音（`pad_ms`），把这截尾巴推出去。
你如果自己写发送端，记得补。

### 4.3 Wi-Fi 省电模式

症状：`ping` 忽快忽慢，25 ms、70 ms、120 ms 乱跳；播放偶尔卡一下。

原因：默认的 `WIFI_PS_MIN_MODEM` 会让射频在没包的时候打盹，醒来有几十毫秒的延迟。

现在固件里 `esp_wifi_set_ps(WIFI_PS_NONE)`。代价是电流多一点——对插电设备完全值得。

### 4.4 麦克风读出来全是 0

不是代码问题，是 INMP441 的 **L/R 脚悬空**。接 GND（左声道）或 VDD（右声道），立刻就有数据。
这个坑值得单独列出来，因为它**不报错**，串口一切正常，只是数据是 0。

### 4.5 用共用的 BCLK 驱动麦克风和功放

试过把两个模块接在同一组 SCK/WS 上省两根线。结果：噪声、偶尔的爆音、以及
「换一块板子就好了」这种无法复现的怪问题。

现在用两个独立 I2S 控制器，各给各的时钟。多花两根线，省下三天。

### 4.6 开头的「毛刺」

症状：每次开始录音，前 0.2 ~ 0.4 秒总是有一下很大的噪声。

原因：I2S DMA 启动瞬间的未初始化数据。**不是硬件故障**，也没法在固件里完全消掉
（清理缓冲区会有别的问题）。

客户端处理：`HELLO` 之后丢掉前 ~300 ms。
所有示例（`examples/vad_record.py`）都这么做了——不这么做，任何能量门限都会被它触发。

### 4.7 拿 UDP 包长估时长

早期用「一包 = 20 ms」数包数算时长，结果和实际差几个百分点。

原因：`i2s_channel_read` 返回的长度不一定正好是 1280 字节，偶尔少一点。
正确做法是**数字节**：`时长 = 字节数 / 64000`。

## 5. 客户端侧的设计建议

这些是「用这套硬件做真东西」时踩出来的，不属于固件，但值得写在同一个地方：

1. **测底噪，别写死阈值**。同一间屋子，开空调前后噪声能差 10 倍。
   拿开头的 0.5 秒算一个百分位数当参考（`examples/vad_record.py` 用 20th percentile）。
2. **要连续两包超阈值才算「开口」**。一包就触发的话，关门声会开始一段录音。
3. **静音判停要给够时间**。人想词的时候会停 1.5 ~ 2 秒，1.2 秒的判停会把你半句话切掉。
4. **播放和录音要用同一个 socket**，理由见 [protocol.md](protocol.md) §2。
5. **别在说话的同时从同一块板子放音**。没有回声消除，麦克风会听到喇叭——
   要么做半双工（说完再播），要么上 AEC（这是另一个数量级的工作）。

## 6. 没做的、以及为什么

| 想要 | 为什么没做 |
|---|---|
| Opus 压缩 | 512 kbit/s 在局域网不心疼；加了编解码就多一层调试面 |
| 回声消除 | 需要在板上做 FIR/自适应滤波，S3 算力可以但工程量翻倍；而且当前是半双工，不需要 |
| mDNS 自动发现 | 板子 IP 从串口看一次就够了；真要做得加 40 行代码和一堆兼容性问题 |
| OTA 升级 | 这是个「放房间里不动」的设备，拔下来插电脑烧一次也就一分钟 |
| 多客户端 | 一个房间通常一个「大脑」；真要做得改 peer 结构，见 protocol.md §7 |
| 电池供电 | Wi-Fi 全开 + 功放，电流下不来；插 USB 才是对的形态 |

---

## 7. 想改成别的东西

- **换采样率**：只改 `config.h` 的 `SAMPLE_RATE`，I2S 会跟着变；但客户端也得改，带宽也变。
- **换引脚**：只改 `config.h` 的六个 `PIN_*`。
- **换成外接功放 / 耳机口**：把 `PIN_AMP_DOUT` 接到外部 DAC 的 DIN，自己算时钟。
- **加第二个麦克风**：`config.h` 里加一个 I2S 通道，包格式要改成「左=麦1，右=麦2」，
  客户端就能做简单的双麦降噪（延时求和）。

改完记得回头看看 §4——你很可能要重蹈里面某一条。
