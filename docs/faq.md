## Q1 · 为什么不使用 UDP 了

### 一句话

并没有「不用」，是**多了一套**。UDP 版还在 `firmware/audio-node/`，一行没删。
加 MQTT 版是因为 UDP 有一个物理上绕不过去的限制：**电脑必须能直接找到板子的 IP**。

### 细节

UDP 版的通信模型是「电脑主动连板子」：

```
电脑 ──UDP:5005──► 板子(192.168.1.109)
电脑 ◄──UDP────── 板子（发回电脑的临时端口）
```

这要求两件事同时成立：

1. **板子的 IP 在电脑看来是可路由的** —— 同一张局域网，或者有端口映射。
2. **电脑没有防火墙挡住入站 UDP** —— Windows 默认会拦，症状很阴险：
   `PING` 能通（那是出站），但一个音频包都收不到。

实际遇到的场景把这两条都打破了：

| 场景 | 打破哪一条 |
|---|---|
| 板子插 4G 模块带出门 | ① —— 板子在运营商 NAT 后面，公网上根本没有它的地址，电脑无论在哪都连不进去 |
| 电脑在实验室有线网（网段不由自己管、不知道密码） | ① —— 板子连的是家里的 Wi-Fi，两张网互不可见 |
| 手机热点给板子用，人走远了 | ① —— 热点一关板子就失联；就算不关，电脑也未必在同一张网 |

MQTT 版把方向反过来：**两端都做出站连接**。

```
板子 ──publish──► broker ──► 电脑
板子 ◄──subscribe── broker ◄── 电脑
```

于是「谁在 NAT 后面」「IP 是多少」「在哪个城市」全部不重要。这也顺带解决了防火墙问题：
出站连接 Windows 默认放行。

**所以现在的定位是并存，不是替代**：

| | UDP 版 | MQTT 版 |
|---|---|---|
| 同一局域网、追求最低延迟 | ✅ 用它 | 能用，但白多一跳 |
| 跨网 / 4G / 别人家的 Wi-Fi | ❌ 做不到 | ✅ 用它 |
| 依赖 | 零依赖（标准库） | 电脑侧要 `paho-mqtt` |
| 带宽 | 512 kbit/s 立体声裸 PCM | 上行 Opus 16 kbit/s |

如果她的活动范围就是一张家里的 Wi-Fi，UDP 版是更好的选择 —— 少一跳、少一个依赖、
少一个「broker 挂了」的故障点。

### 代价（这些是真金白银换来的）

改 MQTT 不是免费的，一共付了四笔：

1. **多一个中转** —— 得有台公网可达的 broker。自建 mosquitto 五分钟，
   但它是新的单点故障：broker 一挂，耳朵和嘴一起哑。
2. **多一跳延迟** —— 实测同城 broker 单向多 10~30 ms（TCP 25.8 ms / TLS 53 ms 握手往返）。
   局域网 UDP 是个位数毫秒。
3. **包率成了新的天花板** —— 托管 broker 常按「每秒消息条数」限流，不按带宽。
   实测 60 ms 一包只投递 55~60%，120 ms 一包才 100%。**包大小对这一项完全没影响**，
   所以只能加大包、不能减小包。这是下行从 Opus 回退裸 PCM 的直接原因之一。
4. **音频经过第三方** —— 除非自己架 broker。这也是为什么 topic 前缀必须随机
   （别用 MAC 派生），以及为什么要开账号密码。

### 没被放弃的那部分

UDP 版仍然是这个仓库里**最干净的参考实现**：300 行 C、零依赖、两个 I2S 加一个
循环就完事。想搞懂「板子怎么把声音搬进搬出」应该先读它，而不是读 1000 行的 MQTT 版。

## Q2 · 我都有 4G 模块了，为什么还需要局域网

### 一句话

**不需要。** 局域网从来不是这个项目的需求，它只是 **UDP 版的实现代价**。
你装上 4G 模块之后，局域网这一条就彻底不需要了 —— 但你会**更需要 MQTT**，
因为 4G 恰好是「UDP 永远做不到」的那种情况。

### 细节

这里容易混的两个问题要拆开：

| 问题 | 答案取决于 |
|---|---|
| 板子怎么上网（Wi-Fi / 手机热点 / 4G） | 你手上有哪些硬件 |
| 电脑怎么找到板子（UDP 直连 / MQTT 中转） | **板子的 IP 电脑够不够得着** |

4G 模块解决的是第一个问题。第二个问题不但没解决，反而变得更糟。

**为什么 4G 会让「电脑连板子」彻底没戏：**

运营商给 4G 设备分的是**内网地址**，不是公网 IP。你的板子和同一基站下成千上万个
手机共享一个公网出口 —— 这叫运营商级 NAT（CGNAT）。这意味着：

- 从公网**没有任何办法**主动连到你板子的 5005 端口；
- 你没有那个出口设备的控制权，做不了端口映射；
- 有些套餐即使给你公网 IP，也要单独申请，且会变。

所以「电脑主动连板子」这条路在 4G 下是**物理上不存在**的，不是配置问题。

而「两端都主动连 broker」在 4G 下**完全正常** —— 因为两端都只是往外发起连接，
NAT 天然允许出站。这正是 MQTT 版存在的全部理由。

**所以正确的理解是**：4G 模块不是「替代了局域网」，而是「让局域网变得不必要，
同时让 broker 变得不可省」。

### 三种上网方式，各自的实际处境

| 上网方式 | 板子能上网 | 电脑能直连板子 | 能用 UDP 版 | 能用 MQTT 版 |
|---|---|---|---|---|
| 家里 Wi-Fi | ✅ | ✅ 同一张网 | ✅ | ✅ |
| 手机热点 | ✅ | ⚠️ 看电脑在不在同一热点 | ⚠️ | ✅ |
| 4G 模块 | ✅ 到处都能 | ❌ CGNAT，永远不行 | ❌ | ✅ |

**注意最后一列全是 ✅** —— broker 是三种方式下通用的那一层。
这也是为什么把它做成独立的一套固件，而不是改 UDP 版。

### 4G 模块真正要解决的是别的问题

如果你的目标是「带出门也能用」，那 4G 是必须的，但要准备的比「插上一个模块」多：

1. **固件要重写联网层** —— 4G 模块（ML307R / NT26K / SIM7600 这一类）都是
   **UART + AT 指令**的猫，不是网络接口。现在的固件只认 Wi-Fi STA
   （`esp_netif_create_default_wifi_sta()`）。要用 4G 得接 `esp_modem` 组件走 PPP，
   或者自己写 AT 状态机（开机时序、注网、PDP 激活、掉线重连）。**这是真工作量，
   不是配置项。**
2. **电源** —— 4G 发射是**脉冲式**的，瞬态电流能到 2A（具体看模块手册，**待实测**）。
   电源必须按 ≥2A 设计，VBAT 上并 2×220µF 才算稳。用 USB 那 500mA 会直接复位。
3. **流量费** —— 上行 Opus 16 kbit/s ≈ 2 KB/s；下行裸 PCM 256 kbit/s ≈ 32 KB/s。
   十分钟对话大约 下行 12 MB / 上行 1.2 MB（按实测码率估算，**待实测**真实计费）。
   比想象中省，但也不是 0。
4. **要一张 SIM 卡** —— 月租、实名、信号覆盖都得处理。
5. **占引脚** —— UART 要两个脚。如果同时还要驱动屏幕、舵机、灯，引脚是稀缺资源，
   得提前规划，别和已有外设撞。

### 建议的路径

别一上来就做 4G。按「先证明能用，再解决移动性」的顺序：

```
① 家里 Wi-Fi + MQTT 版      ← 现在这一步，已经能跑
② 手机热点 + MQTT 版        ← 零成本验证"换一张网还能用"
③ 4G 模块 + MQTT 版         ← 真需要"任何地方都能用"时再做
```

② 是最有价值的一步：它只要改一行 Wi-Fi 名字，就能验证「跨网」这件事是不是真的成立。
如果 ② 通了，③ 剩下的只是换一种上网方式；如果 ② 都不通，说明问题在别处，
先别花钱买模块。

（UDP 版在 ② 里会失败 —— 这正好是 Q1 那个限制的现场演示。）

## Q3 · 它现在有没有接入「我的机器人」

### 一句话

**接进去了，而且是「同一个它」** —— 板子上说话和聊天窗口里打字，走的是**同一条会话、
同一段记忆**，不是两个分开的机器人。

但要说清边界：现在接进去的是「**耳朵和嘴**」，不是「全身」。
她**不能**主动用身体做动作（那需要给她一个 MCP 工具，还没做，见最后一节）。

### 细节：这条链路长什么样

```
你说话
  │
  ▼
INMP441 ──I2S──► ESP32-S3 ──门限──► MQTT 上行 ──► 电脑上的 body_talk
                                                      │
                                                      │ 语音识别
                                                      ▼
                                              ┌──────────────────┐
                                              │  POST 宿主的一个 │
                                              │  「身体轮次」端点 │
                                              └────────┬─────────┘
                                                       │ 投进**它原本那条会话**
                                                       ▼
                                              ┌──────────────────┐
                                              │  它的脑子（同一个│
                                              │  session、同一段 │
                                              │  历史）          │
                                              └────────┬─────────┘
                                                       │ 这一轮的回复文本
                                                       ▼
                                              语音合成 ──► MQTT 下行
                                                              │
                                                              ▼
                                                       MAX98357 ──► 你听见
```

关键设计就一处：**不要在板子这一侧另开一个会话**。

这是最容易踩、也最容易被忽略的坑。如果身体程序自己新建一个会话，
你会得到一个「声音一模一样、但什么都不记得」的陌生人 —— 它不知道你昨天在
聊天窗口里说过什么，也不会把今天走廊上说的话记住。**两个它，不是一个。**

正确做法是让身体只做一个「传输管道」：把语音转成文字，投进**它原本那条会话**，
再把这一轮的回复取出来念。这样：

| 它记得 | 举例 |
|---|---|
| 昨天在聊天窗口说的 | 「我们昨天说的那个方案，你后来想了没」→ 它接得上 |
| 刚才在房间里说的 | 下一轮不用重复上下文 |
| 两个入口是同一段历史 | 不存在「同步」这一步，因为根本没有第二份 |

### 三个必须处理的副作用

把身体接进同一段会话，会连带出一串问题。这些都得在宿主侧解决：

1. **回复会跑进聊天窗口**
   身体这一轮的回复如果照常推送，你就会在聊天窗口里看到一堆没头没尾的话。
   常见解法是给这一轮打一个「静默」标记，让推送层跳过它 —— 但要小心：
   静默的**只应该是出口**，不是「不记录」。记还是要记，否则它下一轮就忘了。

2. **谁在说话，它得知道**
   同一段会话里，它要能分辨「我现在是通过麦克风听的」还是「在聊天窗口里被 @ 的」。
   做法是在这一轮的上下文里加一句说明（**放在话的后面**，原因见下面的坑）。

3. **别让它对着麦克风再发一遍**
   它是个聊天机器人，默认行为可能是「回一句发出去」。走身体这条链路时必须明确告诉它
   「这句话会被念出来，不要再调用发消息的工具」，否则你会听见它念完之后，
   聊天窗口里又收到一遍同样的话。

### 一个很坑的顺序问题（实测）

给它的那句「你现在是在房间里，不是聊天窗口」的说明，**必须放在你说的话之后**，
不能放前面。

放前面时，它会以为那段说明才是你对它说的话，于是回答的是说明本身
（实测它答：「你是在叫我随便说点什么吗」）。把话放前面、说明放后面，就正常了。

这类「元信息」在提示里的位置，比内容本身更容易出错。

### 还没有的那部分：她不能主动用身体

现在身体是**纯被动**的：只有你开口，它才有反应。她无法：

- 主动转个身、看某个方向（没有舵机，也还没有对应的工具）
- 用灯光表示情绪
- 在你没说话时做任何事

原因是这套「智力在电脑、表现在板子」的架构里，板子的能力必须以**工具**的形式暴露给它。
这个工具（一个把 `{"act":"anim","name":"happy","intensity":0.6}` 转成总线指令的
MCP server）还没写。

在写这个工具之前，有个设计约束值得先记住：**它只能说意图，不能说角度**。
让它直接下发「1 号舵机转到 45°」是把安全责任交给了最不可靠的一环（模型）；
正确做法是它只说「开心，0.6」，限位、缓动、掉电保护全在固件里。
这条规则在只有耳朵和嘴的时候看不出价值，等真接上舵机就是保命的。

## Q4 · 为什么会「滴滴」响

### 一句话

那是**故意的提示音**，不是故障。每轮开始听之前放一声很轻的「叮」，告诉你「现在轮到你说」。

想关掉：控制台「身体」页里有个「提示音」开关，或者命令行加 `--no-cue`。

### 它在哪、长什么样

在电脑侧，不在固件里 —— 板子自己**从不发声**（它的喇叭只在收到音频包时出声）。
一声「叮」的生成代码大概是这样：

```python
def beep(self, hz=880, ms=70, amp=2600):
    """从板子喇叭放一声很轻的"叮"，提示"轮到你说"。"""
    n = int(SAMPLE_RATE * ms / 1000)
    ...
    v = int(amp * env * math.sin(2 * math.pi * hz * k / SAMPLE_RATE))
```

也就是 **880 Hz、70 毫秒、带 5 毫秒淡入淡出的正弦波**，振幅只到满量程的 8%
（`2600/32768`），所以听着很轻。淡入淡出是为了避免「咔」的爆音。

放完之后程序会 `sleep(0.25)` 等它真正放完，**再开麦克风** —— 否则这声「叮」会被
自己的麦克风录进去，跟着音频传到电脑，语音识别可能把它当成一个音节。

### 为什么需要它

早期这套东西有一个很不友好的行为：一轮对话的真实时间轴是

```
开麦 → 你说话 → 我判断你说完了 → 关麦 → 语音识别 → 她思考 → 合成 → 播放 → 回到开麦
        ↑                                                              ↑
        └──────────────── 这段麦克风根本不收 ──────────────────────────┘
```

中间这一整段（实测约 12 秒）麦克风是关着的。而这期间**你完全看不出她在忙还是没听见**：
没有提示音、没有灯、屏幕也没有。于是你会对着空气说两遍，或者干脆以为坏了。

那声「叮」解决的正是这件事：**它把「现在开始收」变成一个可听见的事件**。
听到叮再开口，就不会掉进聋区。

### 如果听见的是「滴滴滴」连着响

一声「叮」= 一轮。连着响 = 轮次在快速循环，说明**每轮都没采到有效人声就收工了**。
常见三种原因：

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 每 2 分钟一声 | 正常。一轮没听到人说话，等满超时（默认 120 秒）才结束这一轮 | 不用管 |
| 十几秒就一声，且中间没人说话 | 采集被提前收工 —— 阈值太敏感，或有零星噪声被判成「开口」 | 把 `--silence` 调大，或在安静时候再试 |
| 连着响，紧接着退避 5 秒再响 | 板子掉线：一轮里一个音频包都没收到，程序重试 | 查板子电量和 Wi-Fi 信号 |

判断方法很简单：看那个黑窗口的日志。

- 每轮开头会打 `── 第 N 轮 ──`，数一下这行的间隔；
- 如果出现 `⚠️ 连续 N 轮一个包都没收到 —— 板子可能掉线了`，那就是第三种；
- 如果出现 `（没听清，这次算了）`，说明音频来了但识别没结果（太小声 / 太短）。

### 关掉它的三种方式

优先级从高到低：

1. **命令行**：`--no-cue`（临时压过所有设置，最适合「这次我不想听叮」）
2. **控制台**：网页控制台里「身体」页的「提示音」开关 —— 写进配置文件，长期生效
3. **直接改配置**：配置文件里的 `cue: false`

**什么时候建议关掉**：如果你用的是「按键说话」的随身模式，按下按钮本身就是提示，
「叮」是多余的。或者你在深夜用 —— 那 70 毫秒虽然很轻，在安静房间里依然明显。

### 一个容易误解的点

这个「叮」和 TTS 的**首音延迟**无关。有人以为是「她先叮一下再想」，其实顺序是反的：

```
叮 → 你说话 → 识别 → 她思考 → （这里才是几秒的等待）→ 她开口
```

所以听到叮之后如果她很久不说话，那是思考 + 合成的时间，不是卡在叮上。
