## Q1 · 为什么不使用 UDP 了

### 一句话

并没有「不用」，是**多了一套**。UDP 版还在 `firmware/audio-node/`，一行没删。
加 MQTT 版是因为 UDP 有一个物理上绕不过去的限制：**电脑必须能直接找到板子的 IP**。

### 细节

UDP 版的通信模型是「电脑主动连板子」：

```
电脑 ──UDP:5005──► 板子(192.168.1.109)
电脑 ◄──UDP────── 板子（发回电脑的临时端口）
```

这要求两件事同时成立：

1. **板子的 IP 在电脑看来是可路由的** —— 同一张局域网，或者有端口映射。
2. **电脑没有防火墙挡住入站 UDP** —— Windows 默认会拦，症状很阴险：
   `PING` 能通（那是出站），但一个音频包都收不到。

实际遇到的场景把这两条都打破了：

| 场景 | 打破哪一条 |
|---|---|
| 板子插 4G 模块带出门 | ① —— 板子在运营商 NAT 后面，公网上根本没有它的地址，电脑无论在哪都连不进去 |
| 电脑在实验室有线网（网段不由自己管、不知道密码） | ① —— 板子连的是家里的 Wi-Fi，两张网互不可见 |
| 手机热点给板子用，人走远了 | ① —— 热点一关板子就失联；就算不关，电脑也未必在同一张网 |

MQTT 版把方向反过来：**两端都做出站连接**。

```
板子 ──publish──► broker ──► 电脑
板子 ◄──subscribe── broker ◄── 电脑
```

于是「谁在 NAT 后面」「IP 是多少」「在哪个城市」全部不重要。这也顺带解决了防火墙问题：
出站连接 Windows 默认放行。

**所以现在的定位是并存，不是替代**：

| | UDP 版 | MQTT 版 |
|---|---|---|
| 同一局域网、追求最低延迟 | ✅ 用它 | 能用，但白多一跳 |
| 跨网 / 4G / 别人家的 Wi-Fi | ❌ 做不到 | ✅ 用它 |
| 依赖 | 零依赖（标准库） | 电脑侧要 `paho-mqtt` |
| 带宽 | 512 kbit/s 立体声裸 PCM | 上行 Opus 16 kbit/s |

如果她的活动范围就是一张家里的 Wi-Fi，UDP 版是更好的选择 —— 少一跳、少一个依赖、
少一个「broker 挂了」的故障点。

### 代价（这些是真金白银换来的）

改 MQTT 不是免费的，一共付了四笔：

1. **多一个中转** —— 得有台公网可达的 broker。自建 mosquitto 五分钟，
   但它是新的单点故障：broker 一挂，耳朵和嘴一起哑。
2. **多一跳延迟** —— 实测同城 broker 单向多 10~30 ms（TCP 25.8 ms / TLS 53 ms 握手往返）。
   局域网 UDP 是个位数毫秒。
3. **包率成了新的天花板** —— 托管 broker 常按「每秒消息条数」限流，不按带宽。
   实测 60 ms 一包只投递 55~60%，120 ms 一包才 100%。**包大小对这一项完全没影响**，
   所以只能加大包、不能减小包。这是下行从 Opus 回退裸 PCM 的直接原因之一。
4. **音频经过第三方** —— 除非自己架 broker。这也是为什么 topic 前缀必须随机
   （别用 MAC 派生），以及为什么要开账号密码。

### 没被放弃的那部分

UDP 版仍然是这个仓库里**最干净的参考实现**：300 行 C、零依赖、两个 I2S 加一个
循环就完事。想搞懂「板子怎么把声音搬进搬出」应该先读它，而不是读 1000 行的 MQTT 版。
